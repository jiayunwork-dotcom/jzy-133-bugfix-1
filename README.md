# SPC 均值–极差控制图工具

面向精密轴类零件车间的浏览器端统计过程控制（SPC）系统：录入外径测量值，
**均值–极差（X̄–R）控制图当场更新，Nelson 判异规则实时标色**，过程能力指数
（Cp/Cpk）按基准期冻结统计量给出。

- 后端：Go 1.22 + Echo + PostgreSQL 16（`lib/pq`）
- 前端：Vue 3 + Vite（纯 SVG 自绘控制图，无图表库），nginx:1.27-alpine 托管
- 编排：`docker compose` 三容器（backend / frontend / postgres）

---

## 1. 快速开始

```bash
docker compose up -d --build
# 浏览器打开 http://localhost:8088
```

## 2. 核心概念与工作流

**监控对象（target）**：一台机床的一个尺寸。单独建档，配置：
规格上限 USL、规格下限 LSL（**允许只填单侧**）、子组容量 n（2~10）、
启用哪些判异规则（4 条可单独开关）。

**测量点入序 → 切组**：测量值是全局点序（`measurements.seq`）。两种录入方式：

1. **自动分组（流式）**：逐个输入或粘贴一列数（空格/逗号/换行/制表符分隔），
   数量任意，按服务器点序连续入序，每凑满 n 个点切一个子组。不足 n 个留在
   「待成组散点」里，下次提交自动在队头续拼。
2. **整组提交**：页面给出 n 个输入框，本次必须恰好 n 个值，单独成一组。
   若该档流式录入还留着散点，整组提交会被拒绝（否则检验员会误以为自己提交的
   值就是一个完整子组），提示先补齐或改用自动分组。

**两阶段控制限**：

1. 先录入 **至少 20 个子组**，在「基准与过程能力」面板指定基准期（起止组号）
   点「冻结控制限」。后端用基准期子组算出 X̄̄、R̄、UCL/LCL（Xbar 图与 R 图）
   并**冻结入库**，同时算出基准期 Cp/Cpk。
2. 之后新录入的子组**只按冻结限判定，绝不回算**。
3. **重新基准必须显式发起**。旧限自动关闭并留档，新限从「基准期结束组 + 1」
   起开放；**重新基准只管之后新录的子组，不重判任何旧点、不改任何旧归属**。
   图上用竖虚线标注真正换限判定的位置，每段控制限各自画出。

**点与告警归属（重要，两套相互独立的概念）**：

- **判定归属是落库事实**：`subgroups.baseline_id` / `alarms.baseline_id` 在
  子组**切出/判定的那一刻**盖到当时的开放限上，之后无论再重新基准几次、
  基准期取哪一段（哪怕跨着旧限生效区间）、服务是否重启，都**不再改变**。
  告警的 `(target, rule, triggerSeq)` 主键保证它一生只属于一套限。
- **生效区间是元数据**：`effective_from = 基准期结束组 + 1`，旧限
  `effective_to = effective_from - 1`，只描述「这套限从哪个组号起是开放限」，
  **不用来反推点的归属**。基准期跨在旧限生效区间中间时（典型：旧限已判到
  第 40 组，基准期取 11~30），旧限区间记为 ..30、新限从 31 起开放，但
  31~40 这些重基前已判定的点**仍挂旧限**——于是新限段（31 起）与其首批
  实际判定点（41 起）之间有一段「归属先存、限段后接」的空隙。这是刻意的：
  区间可以重叠/留空，归属不可以漂移。
- **基准期参考是独立的展示属性**（`refBaselineId`）：一个点可以既按 v1 判定
  过，又被后来的 v2 选作参考期。它的判定归属仍是 v1，只是图上可额外提示
  「兼作 v2 参考点」；参考期本身的点不按由自己算出的限判异。
- **查看时绝不按生效区间现算归属**：现算会把「曾按旧限判定、又落进新基准
  参考期」的点算成新限参考点（灰点），并把旧限下的告警改挂到新限名下——
  这正是本工具曾出现过的缺陷。落库归属 + 区间元数据两者分开后，视图是
  纯读取，重启、补录、连续重基都稳定可复现。

**连续两次重新基准、中间没有新子组**：

- 两次基准各自留档，统计量完整保留；后一次基准的开放区间正常记录，但它
  **判定 0 个子组**（基线表的「判定子组数」列显示 0（未判定），图上不为它
  画限段、不画分界线）；
- 之后录入的下一个子组**直接归最新开放限**；历史点与历史告警一条不动。
  规则上禁止这种「空判定版本」没有收益（它不产生任何错误判定），允许它
  反而让「改主意、重选一段基准」成为无损操作，代价只是多一行留档。

**判异（Nelson 1~4，只作用于 X̄ 图；R 图只展示不判异）**：

| 规则 | 内容 | 触发窗口 |
|---|---|---|
| 1 | 一点超出 ±3σ（严格超出控制限，恰在限上不算） | 1 点 |
| 2 | 连续 9 点落在中心线同侧（恰在中心线上中断计数） | 9 点 |
| 3 | 连续 6 点递增或递减（相邻持平中断） | 6 点 |
| 4 | 连续 3 点中 ≥2 点落在同侧 2σ~3σ 区（恰压 2σ 线计入；3σ 外的点按同侧计入） | 3 点 |

每条规则可在档案上单独开关；每条告警记录 **规则号、触发子组、涉及的全部子组**。

**过程能力**：按基准期、组内标准差估计 σ = R̄/d₂：

- 双侧：Cp = (USL−LSL)/(6σ)，Cpk = min((USL−X̄̄)/(3σ), (X̄̄−LSL)/(3σ))
- 单侧：只给对应侧 Cpk，Cp 留空（前端显示「—（单侧规格）」）
- 存在任何告警点时，指数照常计算，页面标注 **「过程不受控，能力指数仅供参考」**

## 3. 判异评估策略：方案、理由与代价

**选定方案：服务端事务内，按「每一套冻结限 + 归属它的点」分别做纯函数
从头重放；告警按键 `(target, rule, triggerSeq)` 在该限分区内幂等合并——
只插入新出现的，从不删除、从不改挂。**

实现位于：

- `internal/domain/alarms.go` 的 `Evaluate`：输入「有序均值点 + 冻结的
  center/UCL/LCL + 启用规则集」，输出告警列表。**纯函数、无状态**。
- `internal/service/evaluate.go` 的 `evaluateBaselineInTx`：对**某一套具体
  的限**，只加载 `subgroups.baseline_id = 该限` 的子组喂给 `Evaluate`，再与
  该限名下已有告警键比对。录入后只重放本次切组归属的那套限；重新基准
  不触发任何重放（旧限不动、新限此刻还没有点）。

**为什么这样选**（题目允许三选一：增量窗口状态 / 尾部重评估 / 从头重放）：

1. **一致性天然成立**。规则 2/3/4 都跨窗口依赖历史点，增量维护四套滑动窗口
   状态最容易在并发、重新基准、规则开关变更时累积状态 bug；重放无状态，
   「同一段数据反复评估」由纯函数性质保证完全一致（见
   `TestRepeatedEvaluationDeterministic`）。
2. **在线追加 ≡ 一次性重放**。每次录入等价于「把同一套限的点从头再评估
   一遍」，触发键只增不减，因此逐点在线追加累积出的告警集合与对该限整段
   一次重放的结果完全相同（见 `TestOnlineAppendEqualsFullReplay`）。
3. **已出告警不会因后来的点消失**。落库是 `ON CONFLICT DO NOTHING` 的只增
   写入；新点最多让告警键集合变大。重新基准不触碰任何旧限的数据：既不
   重放旧限，也不把旧点喂给新限，所以旧告警一条不多、一条不少、不改挂。

**代价**：每次录入 O(k)（k = 当前开放限名下的子组数）。车间每 2 小时一个
子组，一年约 1000~3000 点，纯算术重放为微秒级，完全可接受；真正的 I/O 是
一次区间查询。未来若数据量到几十万点，可退化为「尾部缓冲 + 周期全量校验」
的混合方案，接口无需变化。

### 3.1 窗口规则（规则 2/3/4）跨不跨限版本？——**不跨，窗口在版本处重置**

规则 2（连续 9 点同侧）、规则 3（连续 6 点趋势）、规则 4（3 点中 2 点在
2σ 区）都要往前数若干个点。**新限刚生效的头几个点，不把旧限下的点算进
窗口**：某套限重放时，输入只含归属它自己的点。

- **理由**：① 新限的中心线/σ 是从新基准期算出来的，「点在中心线上/下」
  「距中心几个 σ」只对新中心线有定义，拿旧限下的点对新中心线数同侧、
  数 2σ 是在混用两个总体；② 新限的意义就是「从这里开始按新状态观察」，
  跨窗口会让新限刚生效就背着旧过程的历史触发告警，违背重新基准的初衷；
  ③ 实现上零额外状态，纯函数按归属过滤输入即得。
- **代价**：换限后规则 2/3/4 有一个最长 8 个点（规则 2）的「重新暖机期」，
  期间即使把旧点算进来本该响的告警也不会响。规则 1（单点越限）不受影响、
  无暖机期。这与控制图实务中「重新基准后重新计数」的通行做法一致。集成
  测试 `TestIntegrationGrinderRebaselineDossier` 断言：v2 下第 8 个同侧点
  （48）规则 2 **不**响、第 9 个（49）才响，且涉及窗口恰为 41~49，不含任何
  v1 的点。

### 3.2 归属是「判定时落库」还是「查看时现算」？——**判定时落库**

`subgroups.baseline_id` 与 `alarms.baseline_id` 在判定那一刻写入，视图只读
（见第 2 节「点与告警归属」）。

- **理由**：基准期允许跨在旧限生效区间中间（如 11~30，而 31~40 已按旧限
  判定），此时「按生效区间现算」没有唯一正确答案——21~30 既是旧限判定点、
  又是新限参考点；31~40 在区间上已落入新限范围，事实上却从未按新限判过。
  只有「判定那一刻归属谁」是唯一确定的事实，把它落库，其余查询都变成
  无歧义的直读，重启/补录/再重基结果恒等。
- **代价**：多两列外键与两个索引。升级时迁移 `0002_attribution.sql` 对
  历史数据按旧的生效区间做一次**尽力**回填，有一个无法消除的固有局限：
  旧库没存归属，像「重基前已按旧限判定、而那次重基把基准期取在旧限生效
  区间中间」的点，其旧限归属事实在旧数据里已丢失，SQL 无法恢复，只能重现
  旧代码当时按区间现算的显示（这类点升级后仍显示新限归属）；0002 之后
  新写入的数据归属在切组事务当场落库，完全准确。查看路径不再能「重算
  纠正」归属，正确性前移到写入事务——而写入本就持有目标行锁，归属与切组
  在同一事务内原子完成。

### 3.3 重新基准时告警的生命周期（显式约定）

- 旧限期间产生的告警**不删除、不按新限重判、不改挂**，作为历史留档；
- 新限只对生效后**新切出**的子组判异，这些点的 `baseline_id` 在切组事务里
  盖到新限；
- 首次基准（此前没有任何限）会把此前录下、参考期之外的未判定子组追认到
  新限并做一次重放，使冻结时刻状态与「当时在线」一致——这是唯一一次给
  历史点盖归属。

## 4. 并发录入如何保证「不丢不重、顺序一致」

`POST /api/targets/:id/ingest` 的整个过程在**一个数据库事务**中执行，第一步就是

```sql
SELECT ... FROM targets WHERE id=$1 FOR UPDATE
```

两个检验员同时往同一档提交时，事务在目标行锁上**串行化**：

- 点序号 `measurements.seq` 用
  `max(seq)+1`（在持锁事务内）分配，两次粘贴的点**不会交错**——一次粘贴的
  整列数在点序上连续；
- 切组从散点队头按 n 个连续切，子组序号连续，`(target_id, subgroup_seq)`
  为主键杜绝重复；
- **子组归属的限版本也在同一事务、同一把锁内盖到行上**。因此「检验员正在
  进行的一次整列粘贴」与「另一人发起的重新基准」也被串行化：这次粘贴切出
  的全部子组要么都归重基前的开放限、要么都归新限，**不会一半旧限一半新限**；
- 提交在组边界（n 的整数倍）原子可见，读端不会看到半个子组。

集成测试 `TestIntegrationConcurrentIngest` 用两个 goroutine 各提 20 个整组，
断言最终恰好 40 组、序号 1..40 连续、每组容量为 n。
`TestIntegrationRebaselineVsConcurrentIngest` 让一次 15 组的流式粘贴与一次
重新基准并发，断言这 15 组归属完全一致，且每条告警挂的限与其触发点归属
一致。

## 6. HTTP API

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/health` | 存活探针 |
| GET | `/api/targets` | 监控对象列表 |
| POST | `/api/targets` | 建档 |
| GET | `/api/targets/:id` | 单个对象 |
| GET | `/api/targets/:id/series` | **主图全量数据**：点（含判定归属 `baselineId` 与参考期标记 `refBaselineId`）、全部限段（含留档、各限 `judgedCount` 判定子组数）、告警（含归属限）、能力 |
| POST | `/api/targets/:id/ingest` | 录入：`{"values":[...], "grouped": false|true}` |
| POST | `/api/targets/:id/baselines` | 发起/重新基准：`{"startSeq":1,"endSeq":20}` |

建档请求：

```json
{
  "name": "主轴外圆 Φ20", "machine": "CNC-07", "dimension": "外径",
  "usl": 20.05, "lsl": 19.95,
  "subgroupN": 5,
  "enabledRules": [1, 2, 3, 4]
}
```

`usl`/`lsl` 传 `null` 或省略表示该侧无规格。所有错误统一为
`{"error": "中文原因"}`，校验类错误 HTTP 400，对象不存在 404。

## 7. 校验清单（前端即时提示 + 后端最终裁决，两边措辞一致）

| 场景 | 提示要点 |
|---|---|
| 测量值不是数字（字符串 / 布尔 / NaN / 空） | 「第 k 个值「x」不是有效数字」；API 层自定义 JSON 解码拒绝非数字类型 |
| 子组容量与档案不符（整组数量 ≠ n） | 「本次提交 x 个值，但档案子组容量为 n」 |
| 上限不大于下限 | 「规格上限(x)必须大于规格下限(y)」 |
| 规格两侧都不填 | 「规格上下限至少填写一侧」 |
| n 不在 2~10 | 「子组容量必须是 2 到 10 之间的整数」 |
| 基准期子组 < 20 | 「基准期至少需要 20 个子组，当前仅 k 个」 |
| 基准结束组超出已有数据 | 「基准期结束子组(第k组)超出已有数据(当前共m组)」 |
| 整组提交但有未凑满散点 | 「该档尚有 k 个未凑满的散点，请先在流式模式补齐或改用自动分组」 |

## 8. 如何核对（与验收点逐条对应）

### 8.1 领域单测（无需数据库）

```bash
cd backend && go test ./...
```

- **Cp/Cpk 关系**（`domain/domain_test.go::TestCapabilityRelations`）：
  均值在规格中心时 Cpk = Cp；规格宽度加倍（6→12）数据不变，Cp 1→2；
  均值平移 10→11，Cp 保持 1、Cpk 降为 2/3；单侧规格只有 Cpk；σ=0 时
  两个指数都为空。
- **每条规则的「恰好触发 / 差一点」**（同文件 `TestRule1..4`）：
  - 规则1：19.0001 触发，恰在 UCL=19 不触发；
  - 规则2：连续 9 点触发（涉及 1~9），8 点不触发，中心线点/两侧交替中断；
  - 规则3：6 连增/连减触发，5 点不触发，持平、先增后降中断；
  - 规则4：3 点中 2 点在同侧 2σ 区触发，1 点不触发，分居两侧不触发，

## 9. 关键设计备注

- **规则只判 X̄ 图**：题目指定的四条 Nelson 规则在实现上全部基于均值点；
  R 图保留 UCL/CL/LCL 供人工发现变异增大，但不产生告警。
- **控制限退化（基准期 R̄=0）**：σ 为 0 时规则 2/3/4 无可靠分区，规则 1
  仍按严格越限判定；Cp/Cpk 为空。正常有变异的过程不受影响。
- **基准期点是参考点，不按由自己算出的限判异**：首次基准的生效起点为
  endSeq+1，基准期内图上画为灰色点，避免凭空制造大量规则 2 告警。参考属性
  （`refBaselineId`）与判定归属（`baselineId`）分开存：后来的基准把旧判定点
  选进参考期，不会改变它的判定归属与颜色，只额外标注「兼作参考」。
- **生效区间不等于点归属**：`effective_from/effective_to` 只登记限的开放
  时段（重基时 from=refEnd+1、旧限止于 from-1）；点和告警归属哪一版限以
  落库的 `baseline_id` 为准。基准期跨边界重基会在「新限开放起点」与「新限
  首个判定点」之间留下空隙，属预期。
- **窗口规则跨版本重置**：规则 2/3/4 的前向窗口不含旧限下的点（见 3.1）。
- **迁移**：SQL 嵌入二进制，启动时按文件名顺序应用并登记到
  `schema_migrations`，每个迁移独立事务。
- **时间/序号**：全部判定只依赖子组序号这一全序，不依赖墙上时钟，因此
  多检验员并发、批量补录时判异结果仍然确定。
